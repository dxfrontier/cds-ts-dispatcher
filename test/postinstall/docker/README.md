# Docker linux postinstall harness

Durable replacement for the ad-hoc "docker linux sample" check. Reproduces the
exact environment that broke consumer installs of
`@dxfrontier/cds-ts-dispatcher`: Linux, Node 22, and `GITHUB_ACTIONS=true` /
`CI=true` / `FORCE_COLOR=3` — the CI-like combination that used to make
`cds env get` (without `--json`) print a colored `util.inspect` dump instead
of JSON and crash the postinstall type generator (see
`postinstall/util/EnvGenerator.ts`).

It asserts that installing the **current working tree**, packed exactly as it
would be published, as a fresh consumer dependency:

- exits `0` (never breaks the consumer's `npm install`)
- produces `@dispatcher/index.ts` containing `export interface CDS_ENV`
- produces `@dispatcher/index.js` (the runtime stub for the `#dispatcher`
  import alias) — see the `EXPECT_INDEX_JS` note below
- wires `package.json` `imports['#dispatcher']`, `tsconfig.json` `include`,
  and `.gitignore`
- took the primary (non-skip) code path, not the `skipWithWarning` safety net
- used the primary programmatic env read: the CLI-fallback notice
  (`used the \`cds env get --json\` fallback`) must not appear in the
  install log
- the generated `index.ts` compiles under `tsc --noEmit --strict` (grep-level
  checks cannot catch an emit bug producing an unparsable interface)
- the `#dispatcher` alias genuinely resolves and loads at runtime (a `.cjs`
  probe written into the consumer package requires it)
- the install log really captured the dispatcher's lifecycle output — a
  positive control that keeps the two "does not contain" assertions from
  going silently vacuous if npm's output streaming ever changes

## Run it

```bash
bash test/postinstall/docker/run.sh
```

Requires a running docker daemon. The script packs the repo root
(`npm pack`) into `consumer/cds-ts-dispatcher.tgz`, builds the image, and
deletes the tarball afterwards (even on failure). A successful `docker build`
is the pass signal — assertions run as part of the build (`verify.js`, the
last `RUN` step in `Dockerfile`); a failed check fails the build with a
non-zero exit and a `FAIL: …` line naming the failed assertion.

## Flipping the Node version

```bash
NODE_VERSION=20 bash test/postinstall/docker/run.sh
```

Defaults to `22` (the version used across this repo's CI).

## The `EXPECT_INDEX_JS` toggle

`@dispatcher/index.js` is written directly by `EnvGenerator` as of the
postinstall env-generation redesign. That is a change to the `.ts` sources
only; the *compiled* `postinstall/PostInstall.js` bundle that actually ships
in the npm tarball (and that this harness installs) is rebuilt separately
(`npm run build`). Until that rebuild happens, a tree with the new sources
still packs the old compiled behavior, which never produced `index.js`
(a pre-existing bug: it tried to spawn the literal executable `'npx tsc'`,
which fails silently).

To validate such a tree, turn the assertion off:

```bash
EXPECT_INDEX_JS=false bash test/postinstall/docker/run.sh
```

Once `postinstall/PostInstall.js` is rebuilt from the updated sources, drop
back to the default (or pass `EXPECT_INDEX_JS=true` explicitly) so the
harness once again proves `index.js` is genuinely produced.

## Why `consumer/` depends on `@sap/cds-dk`

The consumer fixture is otherwise minimal, but it does include
`@sap/cds-dk` (devDependency). That's deliberate, not incidental: the `cds`
CLI binary that `cds env get` shells out to is published only by
`@sap/cds-dk` — the `@sap/cds` runtime package exposes `cds-deploy` /
`cds-serve`, never a `cds` bin. A fixture without `cds-dk` doesn't reproduce
the original incident at all; it hits a different, unrelated failure (the
`cds` binary not resolving, an immediate `skipWithWarning`) before ever
reaching the code path that actually broke (colored `cds env get` output
under `GITHUB_ACTIONS`/`FORCE_COLOR` crashing the type generator). Keeping
`cds-dk` out of the picture would make this harness pass even against a
tree that reintroduced the original bug, as long as the CLI stayed
unresolvable — silently defeating the point of the harness.

Since the env-generation redesign, the primary acquisition path is a
programmatic `@sap/cds` read that never touches the CLI; the CLI survives
only as a fallback tier. `cds-dk`'s presence now makes the harness
*stricter*, not weaker: if the programmatic tier regresses, the CLI would
rescue the install, the fallback notice would land in the install log, and
the notice assertion in `verify.js` would fail the build.

## Files

- `Dockerfile` — `node:${NODE_VERSION}-slim`, installs the packed tarball
  under the incident's env vars, then runs `verify.js`.
- `consumer/` — consumer fixture (`package.json`, `tsconfig.json`,
  `.gitignore`). `consumer/cds-ts-dispatcher.tgz` is generated by `run.sh`
  and gitignored, not committed.
- `verify.js` — plain-Node assertion script, copied into the image and run
  as the final build step.
- `run.sh` — packs the current tree, builds the image, cleans up.

## Caveats

- Needs network access during `docker build`: the `node:${NODE_VERSION}-slim`
  base image layers (first run only, then cached locally) and, every run,
  the `RUN npm install` step pulling `@sap/cds`, `@sap/cds-dk`, and
  `@dxfrontier/cds-ts-dispatcher`'s own dependencies from the npm registry.
- `npm install` is run with `--foreground-scripts`. Without it, npm >=7
  buffers and silently discards a *dependency*'s (not the top-level
  project's) lifecycle-script output unless the script fails — the
  `skipWithWarning` text this harness greps for would never reach the log
  either way, making that assertion vacuous.
- The packed tarball's `postinstall/PostInstall.js` is a pre-built, committed
  artifact — it does not necessarily reflect uncommitted `.ts` source changes
  elsewhere in the working tree until `npm run build` regenerates it. If
  `package.json` dependencies and the compiled bundle's `require()` calls
  ever drift out of sync (e.g. a dependency removed from `package.json`
  before the bundle that still requires it is rebuilt), `npm install` fails
  with `MODULE_NOT_FOUND` — a real bug this harness is designed to catch,
  not a flaw in the harness itself.
